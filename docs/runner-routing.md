# Runner routing and budget admission

The desktop application and `fabrica-runner` share deterministic policy from `runner-core`. Existing `routing::decide` behavior, usage signal parsing/history, Jev eligibility checks, and fallback checks are kept in that core. The Tauri modules re-export those APIs so current UI and run code use the same implementation.

## Eligibility and selection

`routing::route_job` routes the implementer and optional reviewer independently. Production facts come only from the versioned `provider-observations.json` snapshot under the selected data root. Each row is bound to the exact settings fingerprint, configured runtime entrypoint fingerprint, provider/model identity, and observation times. Unknown, stale, unavailable, or mismatched runtime/authentication/health/model/privacy/billing facts block that candidate with a reason; they are never inferred from configuration. Tool and context facts are required only when the task requests them. Legacy tasks use Standard/Balanced, require tools, and make no context-capacity guarantee. Local-only is false unless explicitly requested.

An explicit provider/model override is honored only when that exact candidate remains eligible. If unavailable, the result has no selected route so the supervisor can pause for review; it does not switch providers. Optional candidate allowlists are explicit per task; the default candidate set does not expand beyond the configured selection. Economy ranking uses verified input and output prices multiplied by the task's maximum token envelope, with stable ordering for ties. Paid candidates require fresh verified pricing, both maximum input and output token bounds, and a resulting estimated maximum cost before admission. Unknown billing is blocked. Codex subscription billing remains distinct from local or per-token paid billing; unknown subscription quota is not treated as unlimited. Local candidates are zero-cost only when the backend observation identifies them as local.

The returned `RouteProvenance` records task, runtime, override state, selection reason, estimated maximum cost, pricing verification time, and every eligible/rejected candidate with reasons. Existing `Pace` policy remains the tie-breaker and selection policy outside Economy's bounded-price comparison. Latency is a preference derived from completed-run measurements; it is not a completion-time guarantee.

## Usage and Jev

`UsageSignal` retains provider/model identity, units, source, confidence, collection time, window/reset time, status, and optional note. The existing selector only ranks on fresh comparable measurements; missing, stale, unmeasured, or unlike values remain unknown. Subscription quota is not inferred from tokens, spend, or a Jev response. Unknown quota cannot trigger fallback.

Jev is optional advice over the deterministic eligible set. It receives a bounded, sanitized task summary and route list, never paths, diffs, credentials, or issue bodies. Manual overrides, disabled Jev, no route, or fewer than two candidates skip the call. A choice below the configured confidence threshold or outside the eligible set keeps the deterministic route. Provider handoff remains a recorded terminal checkpoint proposal with a bounded handoff count; it never changes an active provider silently or retries unreconciled side effects.

## Durable reservations

`budgets::BudgetStore` uses a dedicated SQLite file supplied by the caller. Configure a batch policy and a policy for each job before submitting work. Policies bound tokens, estimated/maximum micro-USD cost, cumulative task seconds, and concurrent reservations. `reserve` uses an immediate SQLite transaction to check both scopes against settled measured usage plus all active reservations, so parallel workers cannot oversubscribe an aggregate cap.

Reserve the full admitted envelope before provider dispatch. Each reservation durably records the selected provider/model/runtime and pricing source and verification time. A paid request without a recent pricing-derived maximum cost is rejected. `mark_dispatched` closes the unused-release path. A proven pre-dispatch failure can use `release_before_dispatch`; dispatched work must settle with measured tokens, cost, elapsed seconds, and measurement source. If billing is delayed or unavailable, `settle` marks the reservation unresolved and retains its full envelope against all caps. Later, `reconcile_unresolved` requires an evidence reference and measured values and can run exactly once.

Measured overrun is persisted and stops both batch and job admission. Clear a stop only after updating limits to cover used and still-reserved capacity and calling `clear_stop_after_review` with a durable review reference. An overrun cannot undo provider billing. The supervisor must pass the reservation's token envelope as provider limits and enforce the wall-clock timeout; routing estimates do not themselves stop an already-running provider.

Provider billing can post after a process exits and may differ from estimates. The ledger therefore distinguishes reservation maxima from measured totals, and unresolved reservations continue to consume capacity until reconciled. Aggregate `max_seconds` sums task runtime reservations/usage, which is conservative for parallel tasks rather than elapsed batch wall-clock time.

## Integration boundary

Preview is storage-free and reads the last saved snapshot only. In Fabrica, use **Refresh provider evidence** to explicitly inspect configured runtimes and available models; it does not run model inference. The optional checkbox allows an OpenRouter catalog/authentication network probe. The CLI equivalent is `fabrica-runner provider-observations-refresh --settings <path> --data-root <path> [--live-probe]`. Refresh stores a bounded versioned snapshot atomically. Unknown facts remain visible as candidate-specific blockers.

Preview binds the observation snapshot fingerprint, settings, task requirements, worker, source identities, and an immutable per-task semantic route commitment (selected provider/model/runtime identity, privacy and billing classes, authorized candidate set, required capabilities, and exact paid quote/source and limits). Submit recomputes those commitments and rejects a changed route. Old requests deserialize with dispatch refresh disabled.

Before each implementation or reviewer dispatch, the default behavior remains strict: the saved observation fingerprint must still match, or the job becomes `NeedsInput` before reservation. A user may explicitly opt selected provider kinds into a bounded model-free refresh in the Fabrica plan panel. The consent is persisted in the reviewed batch request and fingerprint. At dispatch the runner refreshes only the exact selected profile/model, keeps the result ephemeral, checks it against the immutable commitment, and records the result before reserving capacity. It never writes the global snapshot, chooses a fallback, changes the paid policy/quote, or starts inference before this check. A changed runtime, privacy or billing class, required capability, paid price/source, settings binding, unavailable route, expired deadline, or failed probe becomes `NeedsInput`; even a lower paid price requires a new preview. Timestamp advancement alone is allowed when paid amounts and source remain identical. OpenRouter dispatch refresh is an explicit network and configured-credential consent; Codex and Ollama refreshes are bounded metadata checks without model inference.

No provider live probe or paid request is needed to test the routing policy. Per-token paid routes additionally require explicit per-job pricing and limits; subscription billing is not represented as an unlimited $0 allowance.
